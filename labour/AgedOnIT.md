# 1．IT業界向け「高齢者雇用社会ガイドライン」16項目

ここでいう社会的ガイドラインは、法律のように会社を直接拘束するものではなく、

> **「IT企業が65歳、70歳、さらに70歳超の人材を活用する場合、社会的に望ましい最低限の考え方」**

として整理するのが適切です。

| No. | ガイドラインに記述するとよい事項          | IT業界での具体化                       | 主な根拠                   |
| --: | ------------------------- | ------------------------------- | ---------------------- |
|   1 | **年齢による一律排除をしない**         | 年齢ではなく技術・経験・職務遂行能力で採用・配置を判断     | 高年齢者雇用安定法、雇用対策法        |
|   2 | **60歳以降のキャリアを事前に設計する**    | 55～60歳頃から65、70、70歳超までのキャリア面談    | 高年齢者雇用安定法、JILPT研究      |
|   3 | **65歳以降も本人の能力・希望を尊重する**   | 「管理職→専門職→顧問」など複線型キャリア           | JILPT No.211           |
|   4 | **70歳までの就業機会を確保する**       | 再雇用、定年延長、定年廃止等を組み合わせる           | 高年齢者雇用安定法              |
|   5 | **70歳超の就業機会も検討する**        | 70～75歳を契約社員、短時間社員、専門職等として雇用     | 高年齢者雇用安定法、JILPT No.303 |
|   6 | **勤務時間を柔軟化する**            | 40→32→24→16～20時間/週など段階的短時間勤務    | エイジフレンドリー指針、JILPT研究    |

# 2．各社の「就業規則」に記述するとよい16項目

こちらは少し性格が違います。

社会的ガイドラインが

> **「社会としてどういう高齢者雇用を目指すか」**

なのに対して、就業規則は

> **「その会社では具体的にどう働くのか」**

を明確にする文書です。

労働基準法89条では、常時10人以上の労働者を使用する事業場について、始業・終業、休憩、休日・休暇、賃金、退職等を就業規則に記載することが求められています。([労働チェック][3])

| No. | 就業規則に記述するとよい事項  | 記述内容の例                  |
| --: | --------------- | ----------------------- |
|   1 | **定年年齢**        | 「定年は60歳／65歳／70歳とする」     |
|   2 | **定年後の雇用制度**    | 再雇用、勤務延長、定年廃止等          |
|   3 | **65～70歳の雇用条件** | 雇用形態、職務、契約期間等           |
|   4 | **70歳超の雇用条件**   | 70～75歳等の契約社員・短時間社員制度    |
|   5 | **契約更新の基準**     | 本人の意思、健康、勤務実績、業務量等      |
|   6 | **契約更新の上限**     | 「70歳まで」「75歳まで」「上限なし」等   |
|   7 | **職務・役割の決定方法**  | 技術者、PM、教育担当、顧問等         |
|   8 | **賃金決定方法**      | 職務、技能、経験、成果、勤務時間等       |
|   9 | **賞与の扱い**       | 支給する／しない、評価方法、算定方法      |
|  10 | **勤務時間の選択制度**   | 40、32、24、20時間/週等        |
|  11 | **勤務日数・曜日の選択**  | 週5日、4日、3日等              |
|  12 | **時間外勤務・休日勤務**  | 高齢者の残業・休日勤務の扱い          |
|  13 | **年次有給休暇**      | 勤続年数・所定労働日数に応じた付与       |
|  14 | **健康・安全への配慮**   | 健康状態に応じた職務・時間・場所の変更     |
|  15 | **教育・リスキリング**   | AI、セキュリティ、クラウド等の教育機会    |

## 3．特に重要なのは「年齢」ではなく「段階的な勤務形態」

私はIT企業向けのモデルとして、次のような規則がかなり有効だと思います。

```text
60歳
 │
 │ 通常勤務
 ▼
65歳
 │
 │ 正社員継続／再雇用
 │
 ▼
70歳
 │
 ├── 40時間/週
 │
 ├── 32時間/週
 │
 ├── 24時間/週
 │
 └── 16～20時間/週
 │
 ▼
70歳超
 │
 ├── 短時間専門職
 ├── 技術顧問
 ├── メンター
 ├── 教育担当
 ├── コードレビュー担当
 └── プロジェクト単位契約
```

これは「70歳になったら一律に辞める」という考え方ではなく、**能力・健康・本人希望・会社の必要性に応じて仕事量を段階的に変える**考え方です。

JILPTの調査でも、70歳代まで雇用する企業では、本人と職場の双方から定期的に希望・役割を聞き、仕事を作り出している事例があります。([JIL 労働政策研究・研修機関][4])

また、RIETIの研究では、定年後の継続雇用者について、専門職や後進教育を担当する場合に仕事満足度や時間当たり賃金が比較的高いことが示されています。これは**IT業界で「ベテランを単純な補助作業に移す」のではなく、専門知識・レビュー・教育を職務として評価する**ことを支持する重要な研究だと思います。([RIETI][5])

## 7．今回のテーマで私なら「16＋16」をこう位置付けます

研究・制度設計としては、単に「高齢者を70歳まで雇用する」ではなく、

**「IT高齢技術者の能力を最大限活用しながら、健康・勤務時間・技術変化に応じて仕事を段階的に変更できる制度」**

とするのがよいと思います。

特に、

> **40時間 → 32時間 → 24時間 → 16～20時間**

という**段階的短時間勤務**を制度として明文化し、同時に

> **開発 → 設計レビュー → 技術指導 → メンター → 顧問**

という**職務の段階的移行**を可能にするのが、IT業界ではかなり合理的です。

これは、今回ご質問の「65歳を超えても働きたいが、健康上40時間勤務が難しくなった場合」にも直接つながります。単なる「高齢者雇用制度」ではなく、**「高齢IT技術者の就業継続モデル」**としてまとめる価値があります。

なお、2026年10月1日からはカスタマーハラスメント対策等についても事業主の義務化が予定されていますので、今後就業規則を作るなら、この改正も織り込むべきです。([厚生労働省][15])

# 1. スキル判定の8課題と解決方法

| No. | 課題                      | 解決方法                                                  |
| --: | ----------------------- | ----------------------------------------------------- |
|  S1 | **評価者が技術を理解できない**       | 自己申告だけでなく、成果物・Git履歴・設計書・特許・論文・障害対応記録等を使う「エビデンス型評価」にする |
|  S2 | **古い技術と新しい技術を単純比較できない** | C、COBOL、アセンブラ、組込み、AUTOSAR、クラウド、AI等を技術名ではなく「能力領域」で評価する |
|  S3 | **本人の自己評価が過大／過小になる**    | 自己評価＋同僚評価＋成果物評価＋面談の360度評価にする                          |
|  S4 | **暗黙知を評価できない**          | 「障害原因を推定する」「設計レビューで問題を発見する」など、経験知をシナリオ試験・ケースレビューで評価する |
|  S5 | **実務経験の価値を数値化しにくい**     | 経験年数ではなく「担当した難易度・規模・責任・成果」で評価する                       |
|  S6 | **資格だけでは実力が分からない**      | 資格を補助情報とし、実務成果・コード・設計・問題解決能力を主要指標にする                  |
|  S7 | **技術スキルが変化する**          | 年1回の固定評価ではなく、スキル台帳を随時更新する                             |
|  S8 | **評価者そのものが不足する**        | 社内に専門家がいなければ、社外専門家、OB/OG、学会・業界団体、複数企業による評価ネットワークを利用する |

### 特に重要な解決策

私は **S1＋S4＋S8** が重要だと思います。

つまり、

> 「技術を知らない上司が5段階評価する」

のではなく、

> **「本人が過去の技術成果を証拠として提出し、専門家がその証拠を評価する」**

方式です。

例えば、

```text
本人
 │
 ├─ GitHub/GitLab
 ├─ ソースコード
 ├─ UML/設計書
 ├─ 特許
 ├─ 論文
 ├─ 障害対応記録
 ├─ 顧客案件
 └─ 後進教育実績
       │
       ▼
  スキル評価エンジン
       │
       ├─ 技術スキル
       ├─ 問題解決能力
       ├─ 設計能力
       ├─ 品質能力
       ├─ 教育能力
       └─ 知識継承能力
       │
       ▼
   スキルプロファイル
```

これは、現在のIT技術者評価にもかなり適合します。2026年の研究でも、AI時代のソフトウェアエンジニアには従来とは異なるコンピテンシーを追加する必要があることが論じられています。([arXiv][1])

という問題があります。

| --: | ---------------------- | ---------------------------------- |
|  W1 | **誰が何をできるか分からない**      | スキルマトリクスを作成し、社員×スキル×レベルで管理         |
|  W2 | **高齢者を年齢だけで単純作業に配置する** | 年齢ではなく職務能力・本人希望・健康状態で配置            |

|  W4 | **ベテランの経験が業務に組み込まれない** | 設計レビュー、障害解析、教育、メンターなどを正式な職務にする     |
|  W5 | **本人と会社の希望が一致しない**     | 年1回以上のキャリア面談で「本人希望×会社需要」をマッチング     |

特に高齢者の業務分担については、JILPTの調査で、能力を発揮するための配慮として**「仕事の分担を調整する」「仕事の量を調整する」**が上位に挙げられています。さらに「労働時間を短縮する」ことも重要な配慮として挙げられています。([JIL 労働政策研究・研修機関][2])

* 中高齢者と若年者のベストミックス
* 高齢者の技のマニュアル化
* 技能伝承方法の教育
* 高齢者自身の新しい能力開発

を具体策として示しています。([ジード][3])

これはIT業界にも非常にそのまま適用できます。

# 3. 賞与用評価の8課題と解決方法

ここが一番難しいところです。

「高齢者の給与・賞与をどうするか」ではなく、

> **「何を成果として評価して賞与に反映するのか」**

を明確にする必要があります。

| No. | 課題                     | 解決方法                      |
| --: | ---------------------- | ------------------------- |
|  B1 | **高齢者だけ評価制度の対象外になる**   | 65歳以上も原則として評価対象にする        |
|  B2 | **上司が技術成果を評価できない**     | 技術評価と人事評価を分離し、専門評価者を置く    |
|  B3 | **売上だけではベテランの価値を測れない** | 品質、障害削減、設計レビュー、教育、知識継承も評価 |
|  B4 | **若手と同じ評価指標では不公平になる**  | 職務・役割ごとの評価基準を設定           |
|  B5 | **短時間勤務者の成果が低く見える**    | 絶対量ではなく「所定労働時間当たり成果」も評価   |
|  B6 | **教育・メンタリングが評価されない**   | 後進育成を正式な評価項目にする           |
|  B7 | **技術の難易度を評価できない**      | 「難易度×成果×影響範囲」で評価する        |
|  B8 | **評価結果が賞与にどうつながるか不透明** | 評価項目・ウェイト・賞与算定式を明示する      |

# 4. IT高齢技術者向け賞与評価モデル

例えば次のようなモデルが考えられます。

| 評価項目     |  比率 | 評価例              |
| -------- | --: | ---------------- |
| 技術成果     | 25% | 設計、プログラム、特許、技術開発 |
| 問題解決     | 20% | 障害解析、原因究明、難問解決   |
| 品質・安全    | 15% | バグ削減、レビュー、品質改善   |
| 知識継承     | 15% | 教育、メンタリング、技術文書化  |
| プロジェクト貢献 | 10% | 納期、顧客対応、チーム貢献    |
| リスキリング   | 10% | AI、クラウド、セキュリティ等  |
| 組織貢献     |  5% | 採用、標準化、社内技術活動    |

これなら、例えば70歳のエンジニアが

> 「最新Pythonを書く量は若手より少ないが、30年間の組込み制御の知識を使って重大障害を解決し、若手5人を育成した」

という場合でも、**技術的価値を賞与に反映できます**。

実際、JILPTの調査では、60歳代前半を対象とした評価制度を導入している企業は当時26.3％にとどまり、評価を賃金に反映している企業は約13％でした。つまり、**「高齢者を雇う制度」と「高齢者を評価する制度」が分離していること自体が課題**です。([JIL 労働政策研究・研修機関][4])

また、2026年のJILPT研究では、65歳以降でも仕事内容の連続性は比較的高い一方、短時間・短日数勤務など柔軟な働き方へのニーズは残ることが示されています。([JIL 労働政策研究・研修機関][5])

という形にすると、単なる高齢者雇用論ではなく、**AI・ソフトウェア工学・人事評価・高齢者雇用を横断する研究**になると思います。

# Q3 IT業界では顧客の規則・習慣を受け入れざるをえず、法律違反、合理的な説明責任の欠如、公序良俗に反した悪習などが蔓延している傾向があるといわれています。製造業では、機械、電気、化学などの物理・化学的な制約により、技術的な合理性が優先するのに対して、ソフトウェアでは十分な評価体制が確立していない傾向がるといわれています。特許、規格、論文と顧客の評価という外部の３６０度評価が大事かもしれません。特に組織内に評価できる人がいない場合の仕組みの提案をお願いします。
A3

はい。ご指摘の問題は、単なる「高齢者雇用」の問題ではなく、**「技術的妥当性を誰が評価するのか」という組織ガバナンスの問題**として捉えると、かなり整理しやすくなります。

特にITでは、顧客の要求が「技術的に正しい要求」とは限りません。したがって、

> **顧客評価＝技術評価**

としてしまうと、顧客の慣行や社内政治に技術者の評価が従属してしまいます。

一方、特許・規格・論文・OSS・技術成果物などは、顧客とは独立した「第三者的な証拠」になり得ます。

実際、厚労省の「職業能力評価基準」も、単なる資格や年齢ではなく、**知識・技術技能・成果につながる職務行動**を基準にする考え方を採っています。([厚生労働省][1]) また、IT検証サービス業については、すでにJEEDが「シニア人材活用」を対象にした業界別ガイドラインを公開しています。([ジード][2])

## 1. 私なら「外部360度評価」をこう定義します

通常の360度評価は、

> 上司 → 本人 → 同僚 → 部下 → 顧客

ですが、IT高齢技術者については、これを拡張して、

```text
                    ┌──────────┐
                    │    本人    │
                    └────┬─────┘
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   上司・人事          同僚・部下         顧客
        │                │                │
        └────────────────┼────────────────┘
                         │
                         ▼
                 ┌─────────────┐
                 │ 技術評価機構  │
                 └──────┬──────┘
                        │
       ┌────────────────┼─────────────────┐
       ▼                ▼                 ▼
     特許             規格              論文
       │                │                 │
       ├────────────────┼─────────────────┤
       ▼                ▼                 ▼
    OSS成果          Git履歴           設計・品質成果
                         │
                         ▼
                  ┌─────────────┐
                  │ 外部360度評価 │
                  └──────┬──────┘
                         ▼
                  スキル・職務評価
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
          業務分担                   賞与
```

とします。

ここで重要なのは、**顧客を「評価者の一人」に格下げすること**です。

顧客の評価は重要ですが、顧客の評価だけで技術者を評価してはいけない、という思想です。

---

# 2. 「評価者が社内にいない」問題の本質

私は、問題を次の3種類に分けるのがよいと思います。

| 問題            | 従来方式     | 提案方式             |
| ------------- | -------- | ---------------- |
| 技術を評価できる人がいない | 上司が評価    | **証拠＋外部専門家**     |
| 顧客の評価しかない     | 顧客評価＝能力  | **顧客評価＋技術評価**    |
| 古い技術を評価できない   | 最新技術だけ重視 | **技術分野を分離して評価**  |
| 暗黙知を評価できない    | 自己申告     | **実績・成果物・事例**    |
| 教育を評価できない     | 売上だけ     | **知識移転を成果として評価** |
| 短時間勤務を不利に評価   | 労働時間×成果  | **時間当たり成果＋役割**   |
| 70歳以上を評価できない  | 一律再雇用    | **専門職・顧問等の職務評価** |

これは研究としても筋が通っています。

IT技術者のスキル評価については1995年から実証研究があり、IT分野では技術変化が速く、スキル評価そのものが難しいことが指摘されています。([サイエンスダイレクト][3])

さらに、2025～2026年には日本のITエンジニアについて「技術革新に伴う能力限界の認識」を測定する尺度の研究も出ています。([J-STAGE][4])

---

# 3. 提案：Skill Evidence Passport

私はこの仕組みに名前を付けるなら、

> **Skill Evidence Passport（SEP）**
>
> **技術スキル証拠パスポート**

とするのが分かりやすいと思います。

「私はC言語が得意です」という自己申告ではなく、

> **「C言語について、これだけの第三者検証可能な証拠があります」**

という方式です。

### 例えば

70歳の組込みエンジニアなら、

| 証拠     | 内容               | 評価への利用  |
| ------ | ---------------- | ------- |
| 特許     | 組込み制御方式の発明       | 発明・技術力  |
| 規格     | AUTOSAR/CAN等への関与 | 標準化能力   |
| 論文     | 制御・OS・ソフトウェア論文   | 理論・研究能力 |
| Git    | OSSへのcommit      | 実装能力    |
| 設計書    | システム設計           | 設計能力    |
| 障害記録   | 原因解析・復旧          | 問題解決能力  |
| 顧客評価   | 顧客からの評価          | 実務貢献    |
| 教育実績   | 若手への教育           | 知識継承    |
| レビュー   | コードレビュー記録        | 品質能力    |
| プロジェクト | 担当範囲・責任          | 実務能力    |

となります。

この考え方には、IT専門能力を実際の成果物・ポートフォリオとスキルフレームワークを対応付けて評価する研究があります。Bowers & Petreは、実世界での成果をポートフォリオとして蓄積し、専門職のスキル記述にマッピングする方法を研究しています。([Oro][5])

---

# 4. 「特許・規格・論文・顧客」の扱いを分ける

ここがかなり重要です。

4つを同じ評価点としてはいけません。

### 技術成果の4つの軸

| 外部証拠     | 主に測れるもの        |
| -------- | -------------- |
| **特許**   | 発明・技術的独創性      |
| **規格**   | 標準化・合意形成・技術体系化 |
| **論文**   | 理論化・分析・再現可能な説明 |
| **顧客評価** | 実務価値・問題解決・信頼性  |

そして、これに

| 内部証拠       | 主に測れるもの |
| ---------- | ------- |
| Git/ソースコード | 実装能力    |
| 設計書        | 設計能力    |
| 障害対応       | 問題解決能力  |
| レビュー       | 品質保証能力  |
| 教育         | 知識移転能力  |

を加えます。

これによって、

> **「顧客には評価されなかったが、技術的には非常に優秀」**

という人も、

> **「顧客には好かれているが、技術的成果が乏しい」**

という人も区別できます。

---

# 5. 外部評価を「技術審査会」にする

ただし、ここで一つ問題があります。

**外部評価者も人間です。**

そこで、個人の外部評価者に依存するのではなく、

### Technical Review Board

を設けます。

例えば、

```text
        Technical Review Board
                  │
    ┌─────────────┼─────────────┐
    ▼             ▼             ▼
  大学研究者     業界専門家     社内技術者
    │             │             │
    └─────────────┼─────────────┘
                  ▼
            技術評価委員会
                  │
          ┌───────┴───────┐
          ▼               ▼
      技術レベル        信頼度
      Level 1～7       A～D
```

とします。

ここで非常に重要なのが、

> **「評価点」と「評価の信頼度」を別にする**

ことです。

例えば、

**AUTOSAR：Level 6 / 信頼度A**

なら、

* Level 6：かなり高度
* 信頼度A：複数の独立した証拠で確認

という意味になります。

一方、

**生成AI：Level 5 / 信頼度C**

なら、

* 本人申告と社内成果しかない
* 外部検証が不足

ということが分かります。

---

# 6. AIを使うなら「評価者」ではなく「評価補助者」

ここは以前の話ともつながります。

私は、

> **AIに人間をA～E評価させる**

方式には慎重であるべきだと思います。

それより、

```text
       各種証拠
          │
          ▼
    ┌───────────┐
    │     AI     │
    │ Evidence   │
    │ Collector  │
    └─────┬─────┘
          │
          ▼
     証拠の分類
          │
   ┌──────┼──────┐
   ▼      ▼      ▼
 特許    Git     論文
   │      │      │
   └──────┼──────┘
          ▼
      Skill Map
          │
          ▼
   ┌─────────────┐
   │ 人間の専門家 │
   └──────┬──────┘
          ▼
       最終評価
```

とする方が安全です。

つまり、

> **AIは「評価する」のではなく、「評価可能な証拠を集め、整理し、説明する」。**

最終判断は人間です。

これは最近のAIエージェント評価研究でも重要になっている考え方で、最終回答だけではなく、実際の実行過程や成果物を検証する方向へ研究が進んでいます。([arXiv][6])

---

# 7. 業務分担まで自動的につなげる

この方式のもう一つの大きなメリットがあります。

Skill Evidence Passportを作れば、

> **「この人に何をしてもらえばよいか」**

まで決められます。

例えば、

| スキル        | Level | 適した仕事         |
| ---------- | ----: | ------------- |
| C          |     6 | 設計・レビュー       |
| C++        |     5 | 設計・実装         |
| AUTOSAR    |     6 | Architecture  |
| CAN/CAN FD |     7 | 障害解析          |
| ISO 26262  |     6 | Safety review |
| Python     |     3 | 軽微な開発         |
| AI         |     2 | 現在は教育対象       |
| 教育         |     7 | メンター          |
| 顧客対応       |     6 | 技術説明          |

となります。

すると70歳でも、

> 「若手と同じ量のプログラムを書く」

必要はありません。

例えば、

**週24時間**

なら、

* 月：設計レビュー
* 火：障害解析
* 木：若手教育
* 金：技術文書・標準化

という仕事にできます。

これは「高齢者だから仕事を減らす」のではなく、

> **「高い専門能力を、限られた労働時間の中で最大化する」**

という考え方です。

---

# 8. 賞与評価も同じ証拠から作る

ここが最も重要なポイントです。

**スキル評価、業務分担、賞与評価を別々に作らない。**

同じEvidence Databaseから3つを生成します。

```text
                 Evidence Database
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       Skill Map     Job Match     Performance
          │             │             │
          ▼             ▼             ▼
       能力評価        業務分担       賞与評価
```

例えば、

> 「若手5人を教育した」

という証拠は、

**Skill**
→ 教育能力 Level 7

**Job**
→ メンター・レビュー担当

**Bonus**
→ 知識継承15%の評価項目

として、同じ証拠を3回利用できます。

# 9. 「顧客評価」をあえて制限する

ここはご指摘の問題意識から、かなり重要だと思います。

顧客評価を、

> **100点中50点**

のように直接賞与へ入れるのではなく、

### 顧客評価の位置付け

```text
技術評価       40%
成果評価       25%
知識継承       15%
品質・安全     10%
顧客評価       10%
```

のようにする。

さらに顧客評価にも、

* 技術的妥当性
* 納期
* コミュニケーション
* 問題解決
* 顧客満足

を分けます。

そうしないと、

> 「顧客の無理な要求を断った技術者」

が低評価になる可能性があります。

逆に、

> 「顧客の要求を何でも受け入れる技術者」

が高評価になる危険があります。

これはご指摘の**「顧客の習慣が技術的合理性を上回る」問題**に対する重要な防波堤になります。

---

# 10. 「法令・規格・公序良俗」を評価軸に入れる

さらに私は、単なるスキル評価より一段上の、

## Technical Integrity Score

を導入することを提案します。

例えば、

| 評価項目  | 内容                   |
| ----- | -------------------- |
| 法令遵守  | 法律・規制に反する要求を拒否できる    |
| 規格適合  | ISO/JIS/AUTOSAR等との整合 |
| 安全性   | Safety/Securityを考慮   |
| 説明可能性 | 技術的根拠を説明できる          |
| 再現可能性 | 他者が検証できる             |
| 独立性   | 顧客・上司の圧力だけで判断しない     |
| 公序良俗  | 不適切な慣行を拒否できる         |
| 技術倫理  | 技術者として適切な判断をする       |

これなら、

**「顧客に気に入られる技術者」**

ではなく、

**「技術的に正しい判断を説明できる技術者」**

を評価できます。

# 11. この仕組みの核心

結局、私なら次の原則を会社規則にします。

> **「技術者の評価は、評価者の知識量だけに依存してはならない。」**

そして、

> **「評価者が評価対象技術を十分理解していない場合、第三者が検証可能な技術的証拠を用いて評価する。」**

さらに、

> **「顧客評価は重要な評価情報の一つとするが、技術的妥当性の最終判断とはしない。」**

とします。

厚労省の職業能力評価シートも、本人と上司がそれぞれ評価し、その認識差を面談で確認する仕組みを採用しています。つまり、**単独の評価者による一発評価ではなく、複数の視点とフィードバックを組み合わせる**という方向性は、既存の公的制度とも整合します。([厚生労働省][7])

また、IT検証サービス業では、すでに「シニア人材活用」を業界単位で整理したガイドラインが存在するので、これを出発点に**「評価者不在の場合の外部技術評価」**を追加する研究は十分に意味があります。([ジード][2])

---

## 12. 研究テーマとしてなら、さらに面白くできます

今回の問題を研究にするなら、タイトルは例えば、

> **「評価者不在組織におけるIT高齢技術者の外部Evidence-Based 360° Skill Evaluation System」**

とできます。

そして研究仮説を、

**H1:** 顧客評価だけによる評価は、技術的能力の評価として不十分である。
**H2:** 特許・規格・論文・成果物・Git等を統合したEvidence-based評価は、評価者不在問題を軽減できる。
**H3:** Skill評価と業務分担を統合すると、65歳以上の短時間勤務者でも専門能力を活用しやすくなる。
**H4:** 技術評価と顧客評価を分離することで、顧客慣行による評価バイアスを低減できる。
**H5:** 同じEvidence DatabaseからSkill、Job Assignment、Bonus Evaluationを生成すると、人事評価の説明可能性が向上する。

とすると、かなりしっかりした研究になります。

そして、これは以前検討されていた**「GitHubのコンパイル・実行エラー、教育動画、技術成果、BOTへの質問等をスキル評価に利用する仕組み」**とも非常に相性がよいです。つまり、**「高齢者専用の評価システム」ではなく、年齢を問わず使える技術者Evidence評価基盤を作り、その上に高齢者雇用制度を載せる**のが、私は一番合理的だと思います。
